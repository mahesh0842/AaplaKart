1. Project Overview

Main aaplakart-app

Customer-facing mobile app built with React Native + Expo 54. Features OTP login, dual-brand mode (AaplaKart & The Waffle Guy), product browsing, cart, checkout with Razorpay, order history, and real-time updates.

Tech: React Native 0.81.5, Zustand, Firebase Auth, React Navigation

Backend aaplakart-backend

FastAPI Python server with 67+ REST endpoints + WebSocket server. Uses Firestore (primary) + SQLite (fallback) + JSON files for data. Firebase Admin SDK for auth. Redis caching with graceful degradation.

Tech: FastAPI, SQLAlchemy, Firebase Admin, Razorpay, Redis

Admin aaplakart-admin

Single-page web admin panel (vanilla HTML/JS). 9 tabs: Dashboard, Products, Orders, Categories, Promos, Shops, Health, API Perf, Config. Real-time updates via WebSocket + polling.

Tech: Vanilla JS, Firestore Web SDK, WebSocket

Delivery aaplakart-delivery

Delivery partner mobile app built with React Native + Expo 54. Order acceptance, real-time tracking with Google Maps, earnings dashboard, and delivery proof capture.

Tech: React Native 0.81.5, Zustand, Google Maps, WebSocket

Services Running: Backend (Port 8000) | Admin Panel (Port 3000) | Main App (Port 8082) | Delivery App (Port 8081)

#1 Accept/Reject Orders Local-Only
App: Delivery   File: src/store/deliveryStore.js (lines 59–67)
Accept/Reject operations only update Zustand local state — NO API call to backend. If the app restarts, all accepted/rejected orders revert. Backend has zero record of partner decisions.

#3 XSS via innerHTML PARTIALLY FIXED
App: Admin   File: admin.js
User input (order names, product names, address text) injected directly into innerHTML without sanitization. An attacker with product creation access could inject malicious scripts visible to all admin users.
Fix applied (May 29): Added escapeHtml() function. Product rendering and error messages now sanitized. Full coverage audit still needed.
#4 Firestore Sync Data Loss Risk FIXED
App: Admin   File: admin.py (auto_archive_delivered_orders)
Fixed May 30: Replaced individual set() calls with Firestore batch writes (single network call). Added synced_to_firestore DB flag + verify-and-clean endpoint with Firestore verification before SQLite delete. Auto-triggered at 20+ unsynced delivered orders. Circuit breaker prevents 429 spam. Admin UI shows live sync status.
#5 No Inventory / Stock Validation
App: Backend   File: app/routes/orders.py
Order placement never checks product stock. Users can order 1000 units of an out-of-stock item. No inventory reservation, no stock decrement on successful order.
#6 Mock Token Spoofing
App: Backend   File: app/routes/auth.py
Mock token format mock-dev-{uid}-{random} uses simple string parsing — anyone who knows the pattern can forge tokens. No cryptographic signature verification.
#7 Payment Endpoints Unauthenticated
App: Backend   File: app/routes/payments.py
Both /api/payments/create-order and /api/payments/verify-payment have NO authentication. Any unauthenticated user can create Razorpay orders or submit fake payment verifications. Amount is checked against Redis but Redis failure = no amount verification.

5. UI/UX Issues

  • 🔴 Not Responsive: Fixed 240px sidebar doesn't collapse on tablets/phones. Tables overflow horizontally with no mobile scroll indicators.
  • 🔴 Table Design: 2px solid black borders on all cells — harsh, industrial look. No alternating row colors.
  • 🔴 No Dark Mode: Zero dark mode support despite being an admin tool used at all hours.
  • 🔴 Zero Accessibility: No ARIA labels, no keyboard navigation, no screen reader support, color-only status indicators.
  • 🟠 Alert Sound Too Aggressive: Repeats every 10 seconds for 2 minutes (12 total alerts). No volume control or disable option.
  • 🟠 No Loading Indicators: Only a global "Loading..." text — no per-operation feedback, no skeleton screens.
  • 🟠 Modal Issues: No focus management, no confirmation before closing with unsaved changes, max-width too large for mobile.
  • 🟡 Shadows Too Subtle: Cards don't visually pop off the page.
  • 🟡 No Empty State Messages: When search yields no results, no feedback to user.
  • 🟡 Date Display: Timestamps sometimes show "N/A" if missing; no timezone handling.

Main Customer App — Minor Issues

  • 🟠 Padding Misalignment: Header padding (14px) vs screen padding (20px) — visual inconsistency.
  • 🟠 CategoryBrowser vs ProductGrid Mismatch: hPadding=16px vs paddingHorizontal=20px — 4px gap difference.
  • 🟡 No Loading Skeletons: Full-screen spinner blocks UI during data fetch.
  • 🟡 Empty States Lack Guidance: Users don't know what to do when cart is empty or no orders exist.
  • 🟡 ProductCard "compact" variant redundant: Only differs by borderRadius (10 vs 12).

Delivery Partner App — Minor Issues

  • 🟠 Online/Offline Toggle Cosmetic: Visual indicator doesn't affect app behavior at all — confusing.
  • 🟡 Color Contrast: Muted text on light background is hard to read in sunlight.
  • 🟡 No Offline Mode: App crashes if API is unreachable — no graceful degradation.

Recommendation: Simplify to Polling-Only

For this use case (food delivery with 5-30 min delivery windows):

✅ KEEP WebSocket for: Admin panel (needs instant order alerts for operations)
❌ REMOVE WebSocket from: Main customer app and Delivery app (5s REST polling already provides sub-5s latency, which is more than adequate for food delivery)

Benefits of removing WS from mobile apps:
  • Reduced battery drain (no persistent WS connection)
  • Simpler code (no reconnection logic, ping/pong, state sync)
  • Less server load (no WS connection per mobile user)
  • Better reliability (REST with retry > WS with reconnect)
  • Easier debugging (standard HTTP tooling)
